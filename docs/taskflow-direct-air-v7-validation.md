# Direct AIR v7 validation

Evidence lives in `/home/shiran/project/aie-toy/results/orbit-direct-air-v7`; v6 artifacts remain intact. `diagnostic-summary.json` records actual status, measurements, numerical errors, and source/plan/AIR/ELF identities. `evidence-manifest.json` inventories raw artifacts.

The initial investigation uses independently compiled **complete main functions** for Gate, Up, activation (`SiLU(G)*U`), Down, and the complete FFN. It does not dispatch a subkernel from a multi-stage ELF. D=2048 and I=11008 remain the real FFN dimensions. Fixture generation supplies independent float64 equations; isolated stage inputs are explicitly rounded to float32 before that stage's reference is computed. Full-program references evaluate the entire independent equation in float64 before rounding the final output. All hardware arithmetic uses FP32 with the existing explicit exp approximation; the original finite check and `atol=rtol=1e-5` are unchanged.

These initial measurements are explicitly marked diagnostics: seed 11, zero warmups, one complete output. They establish correctness and workload scaling for investigation, not multi-seed acceptance or stable performance comparisons. Wall time covers runner buffer staging/synchronization, submission, device wait, readback, and output copying; excludes context creation, reference calculation, numerical checking, and NPZ serialization. `compile.json.seconds` covers the aircc subprocess only; cache state is uninstrumented and no cold compile claim is made.

## Timeout boundary

Installed `multilaunch.py` polls `run.state()` without a host time deadline; a terminal `ERT_CMD_STATE_TIMEOUT` is an underlying runtime/device result. Increasing a Python wait deadline cannot fix that terminal state. `/usr/include/xrt/xrt_kernel.h` documents that a zero host wait timeout blocks until completion.

Local driver source `/usr/src/amdxdna-7.0.0-rc1+git20260310.6b13cb8f4/aie2_ctx.c` defines `HWCTX_MAX_TIMEOUT=60000` and supplies it to the DRM scheduler. Its timeout callback marks jobs timed out, which is translated into `ERT_CMD_STATE_TIMEOUT`. The [upstream Linux v7.0 implementation](https://github.com/torvalds/linux/blob/v7.0/drivers/accel/amdxdna/aie2_ctx.c) contains the same policy. The local source is not proven byte-identical to the loaded in-tree Ubuntu module (`srcversion E4FC5AFFF53D21BC6AFDAE3`), so this is strong corroboration of the measured approximately 63.8-second boundary, not an exact binary provenance claim. The loaded module exposes only `aie2_max_col` and `force_cmdlist`, with no timeout parameter. Debugfs/tracing directories are root-only. No driver/package modifications have been made; a supported bounded extension has not yet been found.

The first M128 activation diagnostic (`diagnostic-m128-activation-r1`) stopped before native lowering with `Permission denied` on the shared compiler executable during a concurrent rebuild. This is infrastructure failure, not a numerical or device result. The first M1 Gate measurement completed correctly, but its wrapper then rejected the one-seed evidence under the ordinary three-seed audit; diagnostic mode now explicitly skips that inapplicable acceptance audit and records its limited scope. Its storage and independent error metrics were separately audited. Invalid initial fixture source directories remain preserved; hardware used the corrected `fixtures/m1-r2` source.

Read-only disassembly of the installed module file adds binary evidence: `aie2_hwctx_init` stores `0xea60` (60000) into its scheduler argument structure, then calls `drm_sched_init`; kernel config has `CONFIG_HZ=1000`. `loaded-module-hwctx-init-disassembly.txt` preserves the instructions and relocations. The module file and `/sys/module/amdxdna/srcversion` match; `timeout-investigation.json` binds the compressed module hash and source version. This inspection copied/decompressed the module to `/tmp` and did not change the installed driver.

## Compiler-issued whole-program partitions

The native C++ compiler emits `orbit.program.partition.v1`: complete source buffer types, a finite sequential invocation schedule, slice bindings, complete FFN templates, and template plan/ABI identities. `scripts/taskflow_direct_air_program.py` consumes this manifest. Python chooses no partition or resource, rewrites no AIR, and performs no neural-network arithmetic. Host work is input slicing/copying, existing XRT runner calls, and output copying. Per seed/template, the existing runner retains system-memory weight BOs (`static_indices`) and temporary scratch BOs (`intermediate_indices`); each command still executes its complete template graph on the NPU. These are system BOs, not claims of persistent AIE local weights.

`ffn-m16-partition-diagnostic-r1` consumed native `build/direct-air-v7/partition-m16-r1/manifest.json` and passed complete Y[16,2048] in **72743.841176 ms** using two actual complete-M8 NPU commands (36396.326912 and 36345.919743 ms). Each command remained below the scheduler deadline. Full-output max absolute error is 1.979060471e-8; normalized L2 is 2.227755011e-6. The maximum template payload is 20480 bytes, matching the native plan, plus the separately reserved 4096-byte stack. `independent-audit.json` verifies actual command events, complete output coverage without overlap, saved per-command outputs exactly matching the assembled output, source/plan/ABI/AIR/ELF identities, and the unchanged complete-reference tolerance. This one-seed measurement is explicitly diagnostic.

Partition-program timing covers the complete sequence: host slice preparation, all first and later runner staging/synchronizations, device submits/waits/readbacks, output assembly, and per-invocation output/checkpoint evidence I/O. It excludes context loading, full input/reference loading, final numerical checks, and final complete-output serialization. This differs from the v6 hot-sample timing boundary; no cross-boundary speedup is claimed. The planned large acceptance mode is explicit `--long-acceptance`: at least three independent seeds, one full program execution per seed, zero warmups. This is numerical long-run acceptance, not a three-hot-sample performance measurement.

The B-panel backend fix was tested in `program-bpanel-minimal-r2`: fresh native lowering of the same literal archived Taskflow produced four panel-scope GEMM stages plus scale. The final runtime DMA auditor passed all producer/consumer byte counts **before XRT context creation**. The complete Y[32,64] output passed in 19.482223 ms, max absolute error 7.152557373e-7, and actual maximum local payload 9728 bytes matched the plan without additional payload. The failed r1 artifact remains preserved; its final runtime audit identified a missing A producer (expected 65536 bytes, actual zero). This one-sample success is not a speed comparison.
